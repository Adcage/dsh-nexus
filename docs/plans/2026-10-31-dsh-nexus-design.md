# DSH Nexus 设计记录

日期：2026-10-31

状态：规划中。本文记录已确认决策、设计方向及待讨论事项，不表示实现已经完成，也不是最终实施任务清单。

## 1. 定位

项目名：`dsh-nexus`。

DSH Nexus 是面向 DeepSeek Harness 的可配置工作台。用户可以在同一个插件内，选择、配置和组合工具、提示词、子 Agent 等能力，并把不同组合保存为 DSH 预设。

目标不是再造一套 Agent 框架，而是在尽可能复用 DSH 执行、会话、权限和界面机制的基础上，提供更清楚、更精简、可按个人习惯装配的使用方式。

### 已确认的产品原则

- 同一个插件包，内部模块化，不把每项功能拆成独立安装包。
- 功能可以选择启用和装配，不强迫所有用户采用同一套习惯。
- 前期讨论确认的使用方式，保留为当前用户的默认方案，而不是强制所有装配采用它。
- 支持保存多套装配方案，各自对应一个 DSH 预设；安装插件只需一次。
- “日常开发”“轻量开发”等名称只是说明示例，不表示必须预置这些方案。
- 完整目标分步骤实现、测试和集成；不能以“基础部分可用”为理由，省略已确定的复杂能力。
- 当前尚未开始编写插件代码、安装依赖或修改 DSH 配置。

## 2. 模块化与装配

### 已确认

- 提供统一控制台，不同功能在不同子页面配置。
- 新功能可以增加对应子页面和模块，不必重做整个界面。
- 关闭模块必须实际影响它在对应装配中的贡献，而不只是隐藏页面。
- 模块化管理不接管用户安装的其他第三方插件。
- 不创建另一套插件市场或独立插件加载框架来替代 DSH。

### 模块划分草案

以下用于组织讨论，具体粒度仍需确认：

| 模块 | 内容 |
| --- | --- |
| 提示词定制 | 基础提示词、模块库、默认组合、会话覆盖 |
| 文件工具 | 统一读取文本和图片，以及写入和局部编辑 |
| 终端 | 普通执行、后台任务、持久终端和交互 |
| 联网 | 统一联网入口，复用 DSH 后端 |
| 子 Agent | 统一委派、观察、通信和控制 |
| 原生能力接入 | 技能、结构化提问、待办 |

对于替换型模块，可以考虑“使用 Nexus 实现／使用原生实现／不提供”三种选择。这比单纯开关更容易解释，但三态选择的具体覆盖范围尚未最终确定。

依赖处理、装配编辑方式、方案复制与删除行为，以及装配变更怎样作用于已有会话，仍需细化。不能把已确定的“提示词应用规则”未经讨论推广到所有运行时模块。

## 3. 与原生和第三方能力的边界

### 已确认

- 新建独立预设，不直接修改原生预设或 DSH 安装文件。
- 在 Nexus 装配内替换指定原生工具，不建立限制所有扩展的全局白名单。
- 用户安装、启用的第三方插件，按插件自身机制提供工具；Nexus 不额外封禁。
- 核心工具数量不是模型最终可见工具数量的硬上限。
- 主题、文件树、费用统计等界面功能，不因工具精简而关闭。
- 权限、安全策略、文件保护、上下文管理等不能当作普通工具一并删除。

### 需要验证

- 不主动屏蔽，并不等于第三方插件天然兼容新预设。
- 某些插件可能只适配原生预设 ID，需要单独检查。
- 用户此前提到的 billion-context 等上下文插件，需要验证新预设适配情况及是否与原生压缩重复运行。
- 若被替代工具由宿主全局提供，需要确认能够只处理目标定义，而不误伤第三方工具或其他会话。
- 自定义工具的结果展示、历史回放和原生界面的兼容性需要实际验收。

## 4. 默认工具方案

以下是当前用户已确认的默认方向，不限制其他装配的组合。

| 工具 | 方向 |
| --- | --- |
| `read` | 一个入口读取文本和图片，内部识别类型；文本支持分页 |
| `write` | 创建文件或完整写入文件 |
| `edit` | 精确局部替换；同一文件支持一次提交多处修改 |
| `shell` | 统一终端执行、后台与交互能力 |
| `web` | 统一联网入口，后端优先复用 DSH |
| `agent` | 统一子 Agent 委派与管理 |
| `skill` | 沿用 DSH 原生机制 |
| `ask_user_question` | 保留 DSH 原生结构化提问 |
| `todo_write` | 保留 DSH 原生待办 |

### 搜索与文件操作

- 文件发现、内容搜索默认交给终端，提供自由组合命令的空间。
- 不强制把 `glob` 和 `grep` 合并为一个搜索工具。
- 如提供专用搜索选项，二者应保持独立；是否作为可选模块仍待确认。
- 不为减少工具名称而合并所有文件读写操作。
- 文件版本观察、先读后改、原子修改和用户已有工作保护不能因接口替换丢失。

具体参数、编码支持、输出上限、错误格式以及多处编辑的事务边界，尚需形成详细契约并测试。

## 5. 终端

### 已确认

- 只提供一个统一的 `shell` 入口，不要求模型在多套终端工具之间反复选择。
- 默认 Git Bash，需要时显式选择 PowerShell 7。
- 普通命令默认启动独立进程，不隐式共享 `cd`、环境变量等状态。
- 需要保留状态或连续输入时，显式创建持久终端。
- 后台任务和持久终端是不同能力，独立进程也可以在后台运行。
- 持久终端内部的目录变化，不偷偷改变整个 DSH 会话的工作目录。
- 完整目标包含后台任务、输出续读、交互输入、状态查询、停止和清理。

### 实现与验收注意事项

- 本机所查 DSH 原生 `dsh-bash-local` 明确不支持 Windows；不能直接认为安装 Git Bash 后原生后端就可用。
- Windows 的执行、路径转换、参数传递和进程树清理需要明确适配及测试。
- 不依赖仅在 Pi 启动环境里可见的搜索程序；应明确依赖发现或配置方式。
- 长输出应保留可恢复的完整日志，并提供有边界的继续读取。
- 区分正常退出、非零退出、超时、取消、正在停止及已确认结束。
- 不能把无输出、安静一段时间或已发送停止请求，当作正常完成的证据。
- 不在执行失败后偷偷切换 Shell 重跑，避免重复副作用。

普通执行与持久终端的具体 API、生命周期、任务所有权、重启后的恢复范围仍待讨论。

## 6. 联网

### 已确认

- 复用 DSH 现有可用的搜索和网页读取能力，不新增第三方搜索账号、订阅或密钥要求。
- “不新增付费服务”不等于对现有模型或检索额度作免费承诺，实际费用依 DSH 当前接入方式。
- 为其他服务商预留适配点，但当前不实现其他服务商。
- 后端扩展不应迫使模型更换统一入口的使用方式。

### 接口设计草案

- `search`：提交搜索查询。
- `fetch`：获取指定 URL 的内容。
- `read`：继续读取已经获取的结果。
- `find`：在已获取内容中定位相关片段。

上述操作与参数尚待详细确认，不代表全部可直接从原生接口获得。

### 结果处理方向

- 返回来源、结果标识、必要内容及截断说明。
- 保存实际获取到的内容，以便续读；不能把上游已截断的结果宣称为完整原文。
- 搜索摘要与已读取原文明确区分。
- 外部网页文本是资料，不得当成配置系统指令的来源。
- 不偷偷切换到其他付费后端。

### 已核对的本机实现

DSH CLI 安装包内存在 DeepSeek Messages 搜索后端，以及专用 Search / Fetch API 适配器。Messages 搜索会发起辅助模型请求；专用检索 API 不需要该辅助模型轮次。这里仅核对了随附文档和实现，没有验证当前 Profile 的实际选择、账号权限、可用性或计费。

## 7. 技能、提问和待办

### 技能

- 沿用 DSH 原生注册、发现、目录更新和加载机制。
- 不复制技能文件，不维护 Nexus 专属技能白名单。
- 用户后续在 DSH 支持的位置添加符合格式的技能，沿原生发现与刷新机制进入可用范围。
- 自动加入的是名称和描述目录，完整正文按需加载。
- 尊重技能的模型调用、用户调用等原生标记。
- 子 Agent 根据自身任务加载相关技能，不默认复制父 Agent 已读过的所有技能正文。

### 提问和待办

- 保留 `ask_user_question` 和 `todo_write` 的原生实现。
- 不把与子 Agent 无关的人机提问、待办强塞到 `agent` 或 `shell`。
- 关于何时使用的详细行为规则，不自动扩写进基础提示词；如需要，另行讨论或通过用户选择的提示词模块提供。

## 8. 子 Agent

### 已确认

- 主 Agent 在已授权任务范围内自主决定是否拆分和委派，不要求用户每次明确说“使用子 Agent”。
- 自主委派不等于每个任务必须使用多人协作。
- DSH 内部子 Agent 是默认执行方式，复用原生父子会话和生命周期管理。
- 默认不通过终端启动外部 Agent 来替代内部委派。
- 外部 CLI 只作为可选扩展，不参与默认自动调度，不因内部失败而偷偷切换重跑。
- 子任务不能扩大父任务的授权范围或绕过审批。
- 主 Agent 负责检查、整合和验证子任务交付，不把子 Agent 的成功报告当作最终验收。
- 不将固定角色模板变成任务边界；可以按实际任务描述职责。

### 完整设计方向，细节待确认

- 独立上下文与继承父会话快照。
- 启动、列出、查看状态和读取输出。
- 完成通知、后续通信、中断和停止。
- 在后端支持范围内继续已有子会话。
- 并行、顺序协作及结果汇总。
- 不同角色、模型、并发与递归限制的配置。
- 多写入任务的目录或 worktree 隔离。

### 界面可见性

- 优先复用 DSH 的内部子会话目录和对话展示。
- 验收不只检查最终答案，还需检查能否找到子任务、打开会话、观察过程、发送补充要求及停止任务。
- 原生界面并不细分全部失败、取消等状态；不能把“不再运行”推断为“成功”。
- 外部任务缺少与内部子会话等价的原生展示，若启用必须明确能力和可见性差异。

### 外部 CLI 扩展方向

- 插件探测已支持、已允许的后端，主 Agent 根据任务选择。
- 查到程序不等于版本兼容、已经登录、额度可用或权限符合任务要求。
- 轻量发现与使用前验证分开，不为探测偷偷发起收费模型请求。
- 不自动安装、升级或登录外部 CLI。
- 不假定 DSH 权限能够直接传递给外部程序。
- 具体支持列表及适配范围尚未确定。

## 9. 基础提示词与附加模块

### 已确认的基础文本

```text
你是一名运行在 DeepSeek Harness（DSH）Agent 框架内的专业编程助手。

你通过读取文件、执行命令、编辑代码和创建文件，高效地帮助用户完成任务，并交付高质量的成果。
```

- 基础部分不额外添加“回复简洁”等行为准则。
- 不自动加入强制规划、固定审查流程等工作方式。
- 不把 Pi 的用户级 `AGENTS.md` 或 `APPEND_SYSTEM.md` 自动复制过来。
- 工具元信息与工具贡献的使用说明，沿工具机制提供，不在基础文本中手写重复清单。

### 附加提示词

- 提供统一模块库，用户创建、编辑、选择和排序附加内容。
- 支持预设默认组合与会话单独覆盖。
- 默认不替用户启用额外行为模块。
- 选中的附加文本与基础文本处于系统指令层，不作为普通用户消息、工作区说明或技能正文注入。
- 不能只靠文字标签“最高优先级”模拟系统角色，需要在实际请求中验证。
- 系统层是应用可配置的指令层，不保证覆盖服务商自身规则、实际权限或模型行为限制。
- 顺序控制排列，不意味着后一段拥有一个更高的指令等级。
- 不用清空全部系统提示词贡献的方式实现，以免移除工具及第三方插件正常提供的说明。

### 与 AGENTS.md 的区别

本机 DSH 的 `dsh-agent-instructions` 将 AGENTS.md 等工作区说明作为用户角色的历史内容加载；该机制与系统提示词注册不同。Nexus 的附加模块应使用真正的系统提示词注册机制，原生项目指令机制仍保持独立。

### 生效方式

- 保存默认组合，供后续新会话使用。
- 用户明确应用到当前会话时，从下一次模型请求开始使用新组合，不要求重新开会话。
- 已发出的请求不被中途改写或强制中断。
- 子 Agent 默认使用创建时继承的组合；如需运行中更新，须另行确定行为。
- 会话继续使用原组合，不代表其内容被降为低优先级消息。

### 明确不做的界面内容

- 不显示配置版本号。
- 不提供提示词版本对比或“有更新可用”提示。
- 不把提示词功能做成版本管理系统。

## 10. 控制台与功能子页面

### 已确认

- 统一入口和公共外壳，不把每项功能散落成无关联的独立页面。
- 各功能有独立子页面，导航、主题和保存反馈保持一致。
- 不同功能分开组织配置，避免一个巨大表单。
- 增加 Nexus 的界面，不替换 DSH 的整个原生设置或产品布局。

### 子页面结构草案

- 概览／功能装配。
- 提示词管理。
- 工具配置。
- 终端配置。
- 子 Agent 配置。
- 集成与扩展。

这些是功能组织示意，不是最终视觉稿；模块装配方案的管理位置尚需整合到导航中。

### 提示词页面保留的功能

- 展示基础提示词。
- 创建和编辑模块。
- 勾选和排序模块。
- 预览拼接后的内容。
- 保存为默认组合。
- 应用到当前会话。

编辑预览不是已经生效的证明；是否正确进入系统层，作为实现与测试要求验证，不强制增加配置版本管理界面。

## 11. 技术基线与实现约束

- 已核对的本机 DSH CLI 包版本：`0.2.1-rc.2`；不据此假定所有其他 DSH 运行实例版本一致。
- 已核对的本机 Pi 包版本：`1.2.0`。
- 面向 Windows，需要确认 Git Bash 与 PowerShell 7 的实际执行环境。
- 优先复用 DSH 的工具注册、系统提示词、技能、子 Agent、设置和界面扩展点。
- 注册和启停需要符合 Cordis 的作用域与清理机制。
- 配置与界面必须只作用于预期的 Nexus 装配，不污染其他原生预设。
- 用户输入的提示词按字面处理；不擅自执行其中的模板表达式或把花括号内容当成宿主变量。
- 不把密钥、私有服务地址或环境特定路径写死在代码中。
- 不直接改写用户现有 Profile 文件来代替受支持的插件安装和配置操作。

## 12. 尚待讨论和确认

1. 装配模块的最终粒度，以及哪些替换型能力采用三态选择。
2. 多套方案怎样创建、命名、复制、删除；已有会话关联方案变更时如何处理。
3. 基础提示词是否只展示，还是允许用户在装配中自行修改。
4. 文件工具、终端、联网和子 Agent 的详细参数、输出与失败契约。
5. 模块缺失依赖、实现冲突或后端不可用时的界面与错误行为。
6. 普通命令、后台任务和持久终端在重启、禁用模块及关闭会话时的处理。
7. 子 Agent 的默认模型策略、允许模型范围、并发与递归上限，以及高级编排范围。
8. 原生交付展示、工作目录管理、持续目标、提醒、历史搜索等尚未纳入核心方案的能力如何处理。
9. 工具调用展示模式，以及是否需要 PTC 等可选方式。
10. 当前已安装第三方插件与新预设的兼容性，尤其是上下文管理。
11. 最终导航和视觉设计，以及各设置的装配级／会话级作用范围。
12. 对外发布前的包名可用性、安装与卸载体验。

以上事项尚未形成最终决策，不能直接作为已经批准的实现要求。

## 13. 实施与验证方向

实施任务清单尚未编写。后续可以按以下依赖关系细化，复杂部分仍属于完整目标：

1. 建立插件包、模块组织、DSH 预设及控制台基础。
2. 完成基础文件工具与可验证的普通终端执行。
3. 完成后台、持久和交互终端，以及资源清理。
4. 完成联网结果处理及原生技能、提问、待办接入。
5. 完成内部子 Agent 管理、协作及原生界面兼容。
6. 完成提示词模块、预设默认组合和会话应用。
7. 完成多方案装配、模块启停、第三方兼容及整体回归。

最终顺序仍可调整。每个阶段进行相应测试，不在基础能力通过后就宣布全部完成。

### 验收重点

- 查看实际发送给模型的工具集合，确认被替代原生工具没有重复出现，第三方工具没有被误屏蔽。
- 验证基础和附加提示词的真实系统角色，而不仅是页面预览。
- 验证文件修改保护、并发变更、文本编码与换行等边界。
- 验证图片附件确实进入支持图片的模型上下文。
- 验证日志恢复、进程状态、超时、取消和资源回收。
- 验证子 Agent 的会话可见性、结果回收、通信和停止。
- 验证装配之间、会话之间及原生预设之间的隔离。
- 验证长会话压缩后所需指令和结果引用的处理。
- 通过真实开发任务观察错误调用、参数填写、重复轮询、上下文占用及任务完成情况，不只比较工具名称数量。
- GUI 实际检查与代码、注册状态检查分开报告；未测试的账号能力和外部服务不得宣称可用。
